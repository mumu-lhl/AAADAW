# CLAP instrument helper-process isolation research

Issue: [#200](https://github.com/mumu-lhl/AAADAW/issues/200)  
Scope: cross-platform process boundary for one CLAP instrument; research and implementation tracking.

## Current implementation

- Discovery already launches the current AAADAW executable with a private command, waits with a 30-second deadline, and accepts a versioned JSON response capped at 1 MiB. This isolates plugin entry inspection, but not runtime instances. ([`crates/aaadaw/src/clap_scanner.rs`](../../crates/aaadaw/src/clap_scanner.rs), especially `inspect_entry`, `run_child_with_timeout`, `run_helper`.)
- The scanner uses standard `Command`/`Child` process APIs and a temporary response file. The Rust standard library provides child stdin/stdout/stderr pipes, kill, and wait operations; a runtime helper can reuse the existing executable-dispatch convention while replacing the file protocol with a long-lived stream protocol. ([Rust `Command`](https://doc.rust-lang.org/std/process/struct.Command.html), [`Stdio`](https://doc.rust-lang.org/std/process/struct.Stdio.html), [`Child`](https://doc.rust-lang.org/std/process/struct.Child.html).)
- CLAP instances are currently owned by control-thread owner types; activation allocates host buffers before the processor enters the render graph. The graph calls the instrument synchronously from `AudioRenderGraph::render_into`, after collecting that track's scheduled MIDI, and immediately mixes the resulting block into that track's buffer. ([`crates/aaadaw-engine/src/clap_instrument.rs`](../../crates/aaadaw-engine/src/clap_instrument.rs), `ClapInstrumentOwner::load_from_entry`, `ClapInstrumentProcessor::process`; [`crates/aaadaw-engine/src/lib.rs`](../../crates/aaadaw-engine/src/lib.rs), `AudioRenderGraph::render_into`.)
- Existing realtime policy is to prepare and bound callback buffers/queues, keep graph/plugin setup and teardown off callback, and never wait in callback. The current engine already uses `rtrb` for bounded in-process SPSC handoff. ([`docs/design/realtime-rendering.md`](../design/realtime-rendering.md); [`crates/aaadaw-engine/Cargo.toml`](../../crates/aaadaw-engine/Cargo.toml).)
- ADR 0005 explicitly says runtime CLAP plugins are currently in-process and that crash isolation is later work; scanner isolation does not sandbox plugins or reduce their privileges. ([`docs/adr/0005-clap-midi-instrument-path.md`](../adr/0005-clap-midi-instrument-path.md).)
- Current branch work adds a versioned fixed-layout shared-memory mapping, bounded MIDI/stereo slots, an internal helper command, helper startup handshake, control-thread process ownership/restart, heartbeat detection, and recovery of child-owned slots after confirmed exit. Targeted protocol tests exercise mapped transfer, capacity limits, version mismatch, stalled-heartbeat observation, and dead-helper slot recovery.
- This is an engine foundation only. The desktop app still installs `ClapInstrumentOwner` directly into `AudioRenderGraph`; helper lifecycle is not yet used by playback. Opaque plugin state now crosses the helper boundary through private temporary files, but a real plugin save/restore roundtrip is not yet tested. Graph latency alignment and helper process/fake failure tests remain required. Keep Issue #200 and this roadmap item open until the real playback path and acceptance tests are complete.

## CLAP constraints that shape the protocol

- CLAP marks `plugin->process` as `[audio-thread & active & processing]`; activation is a main-thread, inactive operation that prepares a fixed supported frame range, while start/stop processing are audio-thread operations. A remote protocol must preserve that state machine and send all operations to a single serialized instance owner. ([CLAP `plugin.h`](https://github.com/free-audio/clap/blob/main/include/clap/plugin.h).)
- CLAP defines the audio thread as deadline-sensitive and says to avoid allocation/free, contended locks, I/O, and waiting. A plugin may have sub-millisecond deadlines. Therefore the device callback must never perform a request/response over a pipe/socket, wait for a helper, or take a process-shared lock. ([CLAP `thread-check.h`](https://github.com/free-audio/clap/blob/main/include/clap/ext/thread-check.h).)
- `clap_process_t` carries frame count, transport time, audio buffers, and an immutable sample-sorted event list; event and buffer pointers are only valid during the process call. Remote messages must copy all required fields into owned bounded packets and reconstruct valid per-call CLAP data in the helper. ([CLAP `process.h`](https://github.com/free-audio/clap/blob/main/include/clap/process.h), [`events.h`](https://github.com/free-audio/clap/blob/main/include/clap/events.h).)
- Plugin `process()` may return an error, in which case its output buffer must be discarded. Map a failed/missing/late block to silence and a host-visible fault state; do not replay stale audio as if it belonged to the new transport position. ([CLAP `process.h`](https://github.com/free-audio/clap/blob/main/include/clap/process.h).)
- `clap_host_thread_pool.request_exec` is allowed only in `process()` and blocks until all tasks finish. The first isolated-host slice should not expose this extension: implementing it as IPC from a realtime plugin call would reintroduce a wait/deadline dependency. ([CLAP `thread-pool.h`](https://github.com/free-audio/clap/blob/main/include/clap/ext/thread-pool.h).)
- On Windows and macOS, CLAP's symbolic main thread has GUI/timer constraints tied to the program's actual main thread. Keep the initial scope to instrument audio processing with plugin UI disabled; GUI hosting and main-thread extension callbacks require a separate explicit design. ([CLAP `thread-check.h`](https://github.com/free-audio/clap/blob/main/include/clap/ext/thread-check.h).)

## IPC options

| Design | Advantages | Costs and constraints | Assessment for first isolated instrument |
| --- | --- | --- | --- |
| Synchronous pipe/socket RPC from the audio callback | Small conceptual protocol; no extra render worker. | Pipe I/O and response wait are blocking operations. This violates CLAP's realtime guidance and makes callback duration depend on process scheduling/plugin time. Rust `Child` pipes are ordinary blocking I/O streams. ([Rust `Stdio`](https://doc.rust-lang.org/std/process/struct.Stdio.html), [CLAP `thread-check.h`](https://github.com/free-audio/clap/blob/main/include/clap/ext/thread-check.h).) | Reject. Never call it from the device callback. |
| Dedicated IPC worker + bounded in-process SPSC queues + child stdin/stdout pipes | Uses portable `std::process::Command` and OS pipes; no shared-memory ABI or cross-platform mapping setup. The callback only copies fixed-size MIDI packets into a bounded queue and consumes ready PCM packets; all pipe reads/writes and waiting occur on the worker. The repo already depends on `rtrb`, whose queue is fixed-capacity, lock-free/wait-free, returns immediately, and reports full/empty rather than waiting. ([Rust `Command`/`Stdio`](https://doc.rust-lang.org/std/process/), [`rtrb` docs](https://docs.rs/rtrb/0.4.0/rtrb/).) | Smaller alternative, but it does not meet Issue #200's shared-memory criterion. Do not use as this ticket's transport. |
| File-backed shared-memory SPSC rings + child wakeup | Avoids repeated kernel pipe copies and can support larger/faster multi-instance traffic; fixed slots and atomics are suitable for bounded packet transfer when correctly initialized and synchronized. `memmap2` supplies cross-platform file mappings, but marks file-backed map construction `unsafe` and warns about mutation/truncation from outside the process. ([`memmap2` docs](https://docs.rs/memmap2/latest/memmap2/), [Windows file mappings](https://learn.microsoft.com/en-us/windows/win32/memory/file-mapping), [POSIX `shm_open`](https://man7.org/linux/man-pages/man3/shm_open.3.html).) | Selected for Issue #200. It requires mapping/handle lifetime and permissions, startup handshake, robust process-shared synchronization semantics, wakeups, cleanup after crash, ABI/versioning, and platform tests. `rtrb::RingBuffer::new` allocates its own normal Rust storage; it cannot simply be placed in a mapping and assumed process-shared. ([`rtrb` source/docs](https://github.com/mgeier/rtrb/blob/main/src/lib.rs).) |

`rtrb` is appropriate for callback↔worker queues inside the desktop process, but its existing API is an in-process queue, not a process-shared mapping abstraction. Issue #200 explicitly requires shared memory, so that acceptance criterion overrides the smallest-v1 recommendation above. Use a dedicated mapped-memory protocol with fixed `repr(C)` fields, validated limits, and atomic slot ownership; do not serialize Rust structs or reuse `rtrb` internals across processes. Pipe or thread notifications may wake a non-realtime helper, but shared memory remains the audio/control data path.

## Recommended bounded protocol and callback contract

1. Start one long-lived helper for an instrument from the installed AAADAW executable, analogous to `__aaadaw_scan_clap_entry_v1`. Handshake with a protocol version, plugin entry path/id, sample rate, max frame count, channel layout, event capacity, and requested instance ID. Use a bounded startup deadline. Keep plugin load/init/activate and state restore in the helper's control loop, never the audio callback. Rust child lifecycle primitives include `try_wait`, `kill`, and `wait`; the supervisor must kill and reap on timeout/shutdown. ([scanner implementation](../../crates/aaadaw/src/clap_scanner.rs); [Rust `Child`](https://doc.rust-lang.org/std/process/struct.Child.html); [CLAP `plugin.h`](https://github.com/free-audio/clap/blob/main/include/clap/plugin.h).)
2. Use fixed-capacity shared-memory request/response slots with atomic ownership. Each request contains at most `MAX_EVENTS` compact MIDI/transport events; each response contains at most `MAX_FRAMES × 2` `f32` samples. Allocate and map all storage before playback. Reject or count full/oversized slots; never grow, block, or overwrite unread data on callback.
3. Use a non-realtime wakeup/control path for the helper. Include protocol version, instance/generation ID, monotonic block sequence, absolute start sample, frame count, event count, and status. Validate all counts before use. Treat malformed slots, helper exit, sequence mismatch, and processing errors as instance faults. Drain or redirect child stderr to prevent pipe deadlock.
4. Make the audio-facing API nonblocking and asynchronous. It enqueues the future MIDI block and consumes only the response whose generation/sequence and sample range match the output being rendered. If no matching block is ready, produce silence for that plugin segment, increment an atomic underrun counter, and continue rendering; do not wait for late output or play a stale block. A fixed lead of several blocks absorbs process scheduling jitter but adds real latency. Establish/prime this lead before transport starts and flush/retag queues on seek, loop wrap, graph replacement, stop, and helper restart. Rebuild note/controller chase state at the new start point using the engine's existing MIDI chase model. ([`AudioRenderGraph::render_into`](../../crates/aaadaw-engine/src/lib.rs), MIDI chase; CLAP `process.h`; CLAP `thread-check.h`.)
5. Account for the chosen pipeline latency in the render graph so audio items, instrument output, sends, and downstream effects remain sample-aligned. Current graph code immediately mixes an instrument's just-rendered block into its track buffer; an asynchronous helper must change that seam and must not merely substitute silence-capable IPC under the same synchronous `process()` signature. Latency should be an explicit prepared graph property, and the output FIFO must preserve sample positions across variable callback sizes. ([`AudioRenderGraph::render_into`](../../crates/aaadaw-engine/src/lib.rs); current max-block buffers in [`clap_instrument.rs`](../../crates/aaadaw-engine/src/clap_instrument.rs).)
6. On helper death, stop submitting to its queues, invalidate queued responses, silence only its instrument route, expose a persistent fault, and let transport/audio tracks continue. Do not automatically respawn mid-block; reinitialization, state restore, and note chase belong to a control/supervisor transaction. Scanner behavior already treats child failure as a per-entry error and continues scanning other entries; runtime should preserve the same fault containment at the plugin-instance level. ([scanner error handling](../../crates/aaadaw/src/clap_scanner.rs); [ADR 0005](../adr/0005-clap-midi-instrument-path.md).)

## Cross-platform / safety details

- Prefer inherited stdin/stdout pipes for v1 rather than named pipes: Rust's standard `Command` and `Stdio::piped` work across the project's Windows/macOS/Linux desktop targets without designing named-object permissions or handle passing. Keep binary framing explicit; do not put audio samples through JSON. ([Rust `Command`](https://doc.rust-lang.org/std/process/struct.Command.html), [`Stdio`](https://doc.rust-lang.org/std/process/struct.Stdio.html); current platform targets are documented in [`docs/platforms.md`](../platforms.md).)
- Serialize plugin calls per instance. The helper must ensure `start_processing`, `process`, `stop_processing`, and teardown obey CLAP's thread/active/processing preconditions; only its one CLAP processing thread may call an instance's audio-thread methods at a time. Main-thread-required plugin UI is out of scope until a helper GUI/message-pump architecture exists. ([CLAP `plugin.h`](https://github.com/free-audio/clap/blob/main/include/clap/plugin.h), [`thread-check.h`](https://github.com/free-audio/clap/blob/main/include/clap/ext/thread-check.h).)
- Treat the helper as crash containment, not a security sandbox. It runs with the same user identity and can access user files unless the OS launcher applies a restricted token/sandbox; the existing ADR makes this limitation explicit. ([ADR 0005](../adr/0005-clap-midi-instrument-path.md); OS process launch docs describe creation, not a privilege reduction: [Rust `Command`](https://doc.rust-lang.org/std/process/struct.Command.html).)
- Persist plugin state off the callback. CLAP state save/load interfaces are control-thread work and can involve streams; model these as bounded control messages or separate supervisor transactions, never attach their variable-size data to audio packets. ([CLAP state extension](https://github.com/free-audio/clap/blob/main/include/clap/ext/state.h); [`clap_instrument.rs`](../../crates/aaadaw-engine/src/clap_instrument.rs).)

## Smallest implementation sequence

1. Add a hidden runtime-helper command and versioned load/activate/process/stop protocol for **one MIDI instrument instance**, with fixed packet limits and the helper owning the `ClapInstrumentOwner`.
2. Add callback↔worker bounded SPSC request/response queues and a dedicated non-realtime pipe worker. Keep one helper per instance initially.
3. Add a fixed-latency audio FIFO and graph latency alignment; define queue overflow, helper crash, processing error, stop/seek/loop/graph-swap generation handling, and note chase.
4. Add deterministic tests for protocol validation, size limits, queue-full/empty behavior, process exit/hang, stale-generation rejection, underrun silence, and sample alignment; add platform CI for helper launch on Windows and Linux/macOS.
5. Measure CPU, callback cost, and underruns under a deliberately slow helper before considering helper pooling.

This is a research recommendation, not evidence that the current DAW can already isolate live instrument playback. The existing isolated scanner remains separate; FX hosting, plugin UIs, sandboxing, helper pooling, and offline rendering are outside the smallest v1 slice.
